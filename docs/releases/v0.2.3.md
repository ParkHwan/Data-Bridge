# Data Bridge v0.2.3 — eval safety-net: false-green gate fixed, 3-agent + refusal coverage

> Owner-run/CI evaluation hardening. The agent **serving path is unchanged**; the shipped
> revision `databridge-00006-tdv` differs from prior prod only in the eval tooling + a CI import
> fix, and a prod smoke test confirms identical answer behaviour.
> 🔗 PRs [#9](https://github.com/ParkHwan/Data-Bridge/pull/9) (feature) ·
> [#10](https://github.com/ParkHwan/Data-Bridge/pull/10) (CI import fix)

## 1. Why

The live golden gate was **false-green**. `scripts/run_golden.py` returned
`0 if source_hits == n` — the printed `keyword_hit` never affected the exit code, so keyword
recall could collapse to 0 and the gate still passed. Worse, all 7 golden items were
`knowledge_agent` positives: `data_agent` (BigQuery NL2SQL) and `report_agent` had **zero**
regression coverage, and a product whose identity is *grounded or nothing* had **no refusal
eval at all**.

## 2. What shipped

- **Gate integrity.** Exit code now reflects every observable contract — `keyword_hit >=
  min_keyword`, `expected_final_agent`, tool-call subsequence, citation kind, refusal — not
  just `source_hit`. Per-item state is `PASS / FAIL / REFUSAL_OK / ERROR`; infra errors
  (timeout, auth, BigQuery) are **never** masked as a refusal.
- **New pure `src/databridge/evals/` package** — `observation.py` (snapshot DTO),
  `evaluator.py`, `schema.py` (v2 loader + validation). Imports no ADK / runtime / GCP, so it
  unit-tests fully offline and is reusable as the foundation for a later contract-CI.
- **Golden v2** (`evals/demo_golden.yaml`): knowledge 7 (migrated, no regression) + **data 2**
  (NL2SQL over `thelook_ecommerce`) + **report 1** + **refusal 1**. Schema is versioned and
  strictly validated at load.
- **Observable-surface contract.** The runtime keeps only tool *names* in its trace (payloads
  are dropped), so tool success is judged **indirectly via citations** (a `query_bigquery`
  success ⇒ a `bigquery` citation with SQL). `runtime.py` / `citations.py` / `team.py` are
  unchanged — verified by diff.

## 3. Live verification (owner-run, this release, real Gemini 2.5 Flash + Vertex + BigQuery)

Run by the owner during this release against a local pgvector (docker) with the corpus
re-ingested via Vertex embeddings (24 chunks / 6 docs), `scripts/run_golden.py`:

```
DG-001..007 (knowledge)  PASS   kw=1.000  final=knowledge_agent
DG-008,009  (data/NL2SQL) PASS  kw=1.000  final=data_agent   (bigquery citation, list_tables→query_bigquery)
DG-010      (report)      PASS            final=report_agent
DG-011      (refusal)     REFUSAL_OK
summary: passed=11/11  elapsed=102.94s
```

D-9 finding: the final-response author is **always the specialist** (knowledge/data/report_agent),
never the root orchestrator — `expected_final_agent` in the golden set is set from this live trace.
Offline: 96 tests, `ruff` + `mypy` clean (with the #10 fix, run under the CI condition too).

## 4. Process — 3-party review (Claude / Antigravity / Codex)

6-round design review + 2-round implementation review. The design converged from a naive
"check more fields" idea to an **observable-surface** contract once review established that the
runtime discards tool payloads (so tool-error/`list_tables`-success/row-attribution/refusal-routing
are simply not observable without changing the runtime).

Two evaluator regressions were caught **in implementation review**, not in production:
1. an interim table-parser fix (`allow_empty`) re-introduced a false-green — fully empty rows
   `| | | |` were counted as data rows; and the first empty matching table short-circuited to 0;
2. `evaluate()` sat outside the per-item `try/except`, so an evaluator exception would abort the
   whole run. Both fixed and regression-tested.

A **CI regression escaped implementation review and was caught in this release-note review**:
`test_evaluator.py` imported `run_golden` from `scripts`, which is not an importable package under
the src layout, so the `uv run pytest` gate failed in Cloud Build (build `f81c9813` FAILURE) even
though local `pytest` passed (the rootdir leaked onto `sys.path`). The lesson — impl verification
must reproduce the CI condition (rootdir off `sys.path`), not just run local `pytest` — is now
folded into the process. Fix: PR #10 moved the pure conversion into `evals/adapter.py`.

Reviewer-reliability note carried into global working rules: Antigravity returned "0 issues" each
round while Codex caught the false-green and the CI-import break by reproduction; verdicts were
taken on Codex's findings plus owner re-measurement.

## 5. Production state

- The serving path (`src/databridge/server/`, `src/databridge/agents/`, `citations.py`,
  `runtime.py`) is **unchanged** — verified by `git diff 2b6323c..HEAD`. The change set is eval
  tooling only (`evals/`, `scripts/run_golden.py`, golden data + tests).
- Deploy sequence (this project's Cloud Build runs on every `main` push, no path filter): the
  **#9 merge build failed** at the pytest gate (build `f81c9813`, the CI-import bug), so no
  revision shipped — prod held at `databridge-00005-qfd`. **#10 fixed the gate**; its merge build
  `4247cf47` passed every step — testdb → gates (ruff / mypy / integration tests) → build → push →
  migrate → deploy — and rolled out **`databridge-00006-tdv`** (traffic 100%, image digest matching
  the successful build). An owner prod smoke test (release-cadence question) returned the correct
  cited answer, confirming serving behaviour is unchanged.
- `scripts/run_golden.py` remains an **owner-run** gate (needs live GCP/Vertex/BigQuery); it is
  not part of the automated deploy pipeline.

## 6. Known limitations / deferred

- **Outside the observable surface** (need a runtime that preserves tool payloads → a later
  contract-CI item, "D"): direct tool success/failure, `list_tables` success, report per-row
  source attribution, refusal-time agent/tool routing.
- Still deferred from earlier releases: semantic LLM-judge claim verification ("A"), two-stage
  distance for large corpora ("E"). Korean FTS config is **resolved** (v0.2.1 trigram).
- The `data` golden asserts an answer value/keywords + a `bigquery` citation, but the runtime
  does not expose which returned row a number came from, so "the answer's number is that exact
  cell" is not verified.
