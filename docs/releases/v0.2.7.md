# Data Bridge v0.2.7 — a refusal that can be diagnosed

> `DG-004` failed about half the time and nothing recorded said why, because the runner discarded
> the trace whenever a refusal occurred. Refusals now carry evaluation-only context, and the first
> live run with it identified the cause. No product behaviour changed.
> 🔗 PR [#18](https://github.com/ParkHwan/Data-Bridge/pull/18)

## 1. Why

`DG-004` passed 4 of 9 isolated runs. Every failure ended in `NoEvidenceError`, and every failure
reported zero tool calls — which reads like proof that the agent never searched. It was not proof
of anything: `run_golden.py` caught the exception and built an `Observation` with no trace, so
*every* refusal reported zero calls whether or not a tool had run. That artifact was in fact
misread as a finding during this investigation, and the misreading reached a review request before
the code was checked.

The exception is raised from grounding, after the team has already produced text, so a refusal on
its own says nothing about routing, retrieval, or tool invocation.

## 2. What shipped

- **`NoEvidenceError` carries context** captured where it is still available: the trace, the source
  ids and headings behind the document evidence, per-call search result counts, whether the final
  text was empty and how long it was, the citation count, and which reference markers appeared
  versus how many resolved.
- **Content is excluded when diagnostics are built.** The diagnostic types carry locators, counts,
  lengths and booleans rather than text, and the final trace step is sanitized so it no longer
  carries a preview of the model's answer.
- **Two grounding states are recorded independently.** The code tested "no citations" before "empty
  answer" and raised the same message for both, so the second condition was invisible whenever the
  first held.
- **Refusal items check the process, not just the outcome.** A refusal item now also requires that
  `search_knowledge` completed — reported separately from the existing refusal assertions, and
  skipped entirely when diagnostics are absent so older observations keep their previous result.
  Result count and relevance are deliberately not required, so a genuine "searched and found
  nothing" refusal still passes.
- **The runner prints a diagnostic line** for refused items: tool names, search result counts,
  document and citation counts, booleans and lengths. No query text, no answer text.

The exception message is unchanged, so the API's 422 body is byte-identical, and the `evals`
package still imports nothing from ADK or the runtime.

## 3. Verification

**Offline gates** (`ruff`, `mypy` 33 files, `pytest`): green, and identical under the CI condition
— run from outside the project root with `PYTHONPATH` cleared. As in v0.2.6 the test count depends
on whether the local database is up, so compare like for like.

**Live owner-run diagnosis.** The instrumentation answered on its first run. In the instrumented
refusals of `DG-004` the signature was consistent: the root agent transferred, `search_knowledge`
was called and returned five results, documents became evidence, the model produced text — and
**no reference markers were emitted**, so grounding dropped every line and the answer came out
empty.

For those runs the immediate cause of the grounding failure was marker absence, not routing and not
a failure to invoke the tool. The claim that the agent "never searched" was wrong. Note what this
does *not* establish: five documents returned shows the search ran and returned results, not that
the document able to answer the question was among them.

## 4. Process — 3-party review (Claude / Antigravity / Codex)

The design round introduced a **premise-verification protocol**: the request lists the author's own
claims as numbered premises, and each reviewer must mark every premise either independently
confirmed with a file, line or command output, or accepted on trust. It exists because the previous
round's review inherited a false premise from the request itself and built a prescription on it.

The protocol did what it was meant to. On the release-note round one reviewer confirmed the
repository-verifiable premises and explicitly marked the live-observation ones as trusted rather
than checked — the distinction that matters when a claim rests on a run nobody else can reproduce.
It does not, however, constrain facts a reviewer introduces on its own initiative; those still have
to be re-measured by the author.

Implementation review closed at zero issues.

## 6. Known limitations / deferred

- **The cause of `DG-004` is identified but not fixed.** This release adds diagnosis only; why the
  model omits markers on this question while emitting them reliably on six others is the subject of
  the next round.
- **`DG-004` has at least two distinct failure modes.** Besides the refusal above, one run failed
  as a *grounded* answer with a keyword score of zero — wrong content rather than a missing
  citation. A marker-only fix will not stabilise the item.
- **`DG-011` carries a false-green risk the new process check does not close.** It passes as a
  correct refusal while showing the same signature as the `DG-004` failure: documents were
  retrieved and then not cited. If those documents were all irrelevant, refusing is correct — but
  nothing in the gate establishes that. What is demonstrated is that the evaluator cannot judge
  retrieval relevance or whether a refusal was semantically warranted; the process check only
  requires that the search completed, which it did.
- **Query rewriting cannot be diagnosed directly.** The query text is deliberately not retained, so
  that cause is reachable only by eliminating the others; the docstring says so at the definition.
- **General exceptions and timeouts still lose their trace.** Scope was limited to the refusal path
  by decision, not oversight.
